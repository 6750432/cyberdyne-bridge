## 1. 名词与判定基准

- **主链**：`bridge.py`（脑侧主程序）、`node/server.js`（手侧）、`config.json`（配置）。本项目约定主链只承担接线，新增能力置于 `node/plugins/` 或 `外挂/`。
- **哈希**：`sha256sum bridge.py` 的输出。本公示中若出现 16 位十六进制，均为 SHA-256 的前 16 位；需要完整值处以完整值列出。
- **判定基准**：以可复算的命令输出为准。任何“未改动”的陈述若不能由命令复现，本公示不予采信。

## 4. 变更内容与原因

### 4.1 有明确记载的原因（均对应当前文件内的注释）

| 序号 | 变更内容 | 记载的原因 | 出处 |
|---|---|---|---|
| 1 | JSON 解析的“精准裁剪器”：严格解析 → 闭合块提取 → 基础容错 → 失败即熔断 | 仓库所有者提出“类似 CRISPR-Cas9 的精准裁剪器”设想，用于处理模型输出中的冗余文本 | `bridge.py` 第 2630 行附近注释 |
| 2 | 解析结果增加 schema 校验与熔断 | 仓库所有者补充要求：所有提取出的 JSON 必须通过 schema 校验，字段类型错误或结构残缺不得放行 | `bridge.py` 第 2717 行附近注释 |
| 3 | 异常时输出现场调用栈 | 仓库所有者确认：仅有 `UnboundLocalError: local variable 'd'` 无法定位问题位置 | `bridge.py` 第 3978 行附近注释 |
| 4 | `_多久前()` 缩进修复 | 该函数内 `d = max(0.0, time.time() - float(ts))` 原多缩进四格，落入 `if not ts:` 分支，而该分支首行即 `return`，导致 `d` 永不被赋值，传入有效时间戳时必然抛出 `UnboundLocalError`。发现路径：`tools/测记忆.py` 持续失败，使用 git 原版复现后定位 | `bridge.py` 第 1950 行附近注释（标注 2026-10-10） |

第 3 项与第 4 项存在因果关系：先按建议输出调用栈，随后依据该调用栈定位并修复第 4 项缺陷。

### 4.2 记载缺失的部分

**第 1 代 → 第 2 代**（`2499f81f807431b0` → `15536b020d5583ba`）发生于 2026-10-09 18:59 至 19:04 之间，间隔约 5 分钟。现有材料仅记录“哈希发生变化”，**未记录变更原因**。

同一日仓库所有者曾提出第 4.1 节第 1、2 项需求，但无直接证据表明该次哈希变化由这两项改动造成。因此该次变更的原因在本文中标注为**未记录**，不作推定。第 3、4 代两次短时段哈希同样缺少原因记录。

## 5. 其他需要记录的事实

1. **工作副本未进入版本历史**：`bridge.py` 自 2026-10-10 起的改动未产生任何提交。

   ```bash
   git status --short bridge.py     # 输出 " M bridge.py"
   git log --oneline -- bridge.py   # 最近两次提交均为 2026-10-09
   ```

2. **远端版本仍包含缺陷**：`git show origin/main:bridge.py` 中 `_多久前()` 仍为缩进错误版本，即从仓库克隆所得到的副本会触发第 4.2 节所述异常。

3. **两条历史线无共同祖先**：

   ```bash
   git merge-base HEAD origin/main
   # fatal: HEAD...origin/main: no merge base
   git rev-list --left-right --count HEAD...origin/main
   # 144    5
   ```

   本地历史起于 `4f240b3 M1-M7a stable baseline after M7b rollback`，为细粒度开发记录；远端历史起于 `bcb4d49 2026-10-10 全量同步…`，为快照式记录。两者无法直接合并；若向远端 `main` 直接推送本地历史，将替换远端现有提交线。

4. **当前工作副本可用性**：语法检查通过，且 `tools/测记忆.py` 全部用例通过。

   ```bash
   python3 -m py_compile bridge.py      # 通过
   python3 tools/测记忆.py              # 39 项通过，0 项失败
   ```

## 6. 结论与边界

**已确认**

- `bridge.py` 的哈希发生过多次变更，当前存在三个互不相同的值（工作副本 / 本地最近提交 / 远端 `main`）。
- 当前工作副本可正常编译并通过相关测试。
- 远端 `main` 中的 `bridge.py` 仍包含第 4.2 节所述缩进缺陷。
- 本地历史与远端历史无共同祖先。
- `bridge.py` 自 2026-10-10 起未产生提交。

**尚未处置（待仓库所有者决定）**

1. 是否为当前工作副本补记一次提交，使其进入版本历史，并在提交信息中载明变更内容与依据。
2. 两条历史线如何处置：以本地细粒度历史为准（需替换远端现有提交线），或以远端历史为准（将当前工作副本作为新提交接续）。
3. 仓库内三套哈希登记值是否统一为单一来源（建议统一指向 `tools/跑全部.sh` 中使用的值，并在登记处注明变更时间与原因）。
