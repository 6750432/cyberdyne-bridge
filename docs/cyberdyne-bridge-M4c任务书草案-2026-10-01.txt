# M4c 任务书草案 · 任务栈

> 一句话题目：**让它能"先走到那儿、再挖三个、再回来"—— 中途挨打会先保命，
> 威胁过了接着从断的地方干，干不成就说清为什么。**

主人 2026-10-01 定的三条核心要求（原话）：
① 多步任务（记进度）；② 打断与恢复（**反射层一票否决优先**）；③ 失败重试（并记录原因）。

**2026-10-01 追加的架构原则（主人当场抓到的物理时间维度漏洞）**：
④ **非阻塞条件等待（`wait_until`）** —— 见 §二之三。烧矿石、等作物成熟这类
"任务的完成不取决于我做了什么、而取决于世界过了多久"的步骤，
**绝不能用"动作超时"去套**，也**绝不许阻塞主循环**。

---

## 一、目标

1. **多步任务**：一句话下达一个由多个步骤组成的任务，按序执行，**进度可查**。
2. **打断与恢复**：任何时候反射层（保命 / 反击 / 追猎）都能立刻接管；
   任务**暂停**并把当前步骤记下来，威胁过去后**从断点继续**（不从头再来）。
3. **失败重试**：单步失败按策略重试（有上限、有退避），并**记录原因**；
   重试用完就放弃整个任务，并且**说清楚卡在哪一步、为什么**。
4. **一票否决**：任务永远排在反射层后面。任务不会为了"把活干完"而拖延一次逃命。

**明确不做**（这一轮）：跨重启自动续做、任务优先级抢占、并行任务、任务间的依赖图、
让大模型自由生成任务步骤（白名单仍然不含攻击类）。

---

## 二、任务长什么样

一个任务 = **一串步骤**，每步都有「动作 + 参数 + 完成判据 + 超时 + 重试上限」。
完成判据一律**看事实**（快照里的数据），不认"命令发出去了"——
这是这个项目反复吃过的教训：**没报错 ≠ 生效了**。

| 步骤 | 参数 | 完成判据（看事实） | 失败原因示例 |
|---|---|---|---|
| 走到 | 坐标 | 与目标水平距离 ≤ `到点半径`（默认 2） | 卡住不动 / 超时 / 无路可走 |
| 挖 | 坐标 | 方块探针报这个坐标变成空气 | 挖不动（基岩类）/ 坐标读不到 |
| 拾 | 物品名+数量 | 物品探针报背包里够数了 | 没掉东西 / 够不着 |
| 打 | 目标名 | 目标血量探针 ≤0 或目标从玩家表消失 | 追不上 / 目标下线 |
| 放 | 坐标+方块 | 方块探针报那个坐标变成目标方块 | 放不进去 / 手里没这个方块 |
| 熔炉放料 | 坐标+物品 | 熔炉探针报输入槽里有了 | 不在熔炉旁边 / 手里没料 |
| 熔炉取成品 | 坐标 | 物品探针报背包里够数了 | 还没烧完 / 输出槽是空的 |
| **wait_until** | **条件 + 探针 + 等待超时** | **探针事实满足条件** | **等待超时（不重试，见下）** |
| 等 | 毫秒 | 时间到 | —— |
| 说 | 文本 | 命令已发 | —— |

> 表里的 `等`（固定时长）和 `wait_until`（等条件）是两种东西：
> `等` 是"我知道要多久"（几秒钟的收尾动作），`wait_until` 是"我不知道要多久，
> 我只知道**等什么**"。世界的时间归世界管。

### 二之三 · ★ 非阻塞条件等待（`wait_until`）—— 架构原则

主人 2026-10-01 原话：「等待型任务（如烧矿石、等作物成熟）……你的 60 秒超时和
现有的循环结构会直接把任务判死，而且可能会阻塞反射层的运行。」

这类步骤的**完成时间不由我决定**（一炉铁要 10 秒/个、一组 64 个≈10 分 40 秒；
作物成熟是几分钟到几十分钟）。所以它必须是一条**独立的原则**，而不是"超时调大点"：

**步骤形态**
```json
{ "动作": "wait_until",
  "条件": "furnace_done",          // 条件名（见下表）
  "探针": { "furnace": [x, y, z] }, // 用哪条事实通道判
  "等待超时_ms": 300000 }
```

**四条铁律**
1. **不发手部动作。** `wait_until` 这一拍不下任何命令 —— 它只**读事实**。
   （所以它天生不可能阻塞、也不可能跟反射层抢方向盘。）
2. **不阻塞、循环照跑。** 主循环每一拍问一句"条件满足了吗"，就这么简单。
   绝不允许 `sleep`、绝不允许"卡在这一步等世界"。
3. **反射层永远最高优先级。** 等待期间反射层**照常接管**（跑/吃/反击/追猎）；
   被打就记一条 `暂停（原因：战斗，仍在等待熔炉）`，安全后**无缝恢复轮询**。
   注意这里和普通动作步骤的差别：普通步骤要"交还方向盘"，等待步骤
   **根本没有方向盘**，所以它既不暂停动作、也不丢进度 —— 只是日志上留痕。
   探针在等待期间**照常轮询**（所以"你在打架的时候炉子烧完了"它也能第一时间知道）。
4. **等待超时独立设置，且不计入退避重试。**
   默认 `等待超时_ms = 300000`（300 秒 ≈ 30 个铁矿石）。
   建议算法：`超时 ≥ 要烧的个数 × 10 秒 × 1.5 倍余量`。
   超时**不算"动作失败"**：不进退避重试、不重试，而是**终止这一步并说清原因**
   （"我等了 300 秒，炉子还没烧完，先不干了"）。理由：等待超时几乎总是说明
   **前提不成立**（没放料、没燃料、炉子被拆了），重试只是白等第二个 300 秒。

**条件表（先支持这些，够用又不复杂）**

| 条件名 | 判据（事实） | 例子 |
|---|---|---|
| `item_count` | 物品探针 ≥ N | 背包里有 3 个铁锭 |
| `block_is` | 方块探针 == 指定方块名 | (x,y,z) 已经是 `air` |
| `furnace_done` | 熔炉探针：输出槽非空 | 铁锭烧好了 |
| `furnace_idle` | 熔炉探针：输入槽空且输出槽空 | 料和成品都取干净了 |
| `player_near` | 玩家表：某人距离 ≤ N | 主人走到我旁边了 |
| `hp_at_least` | 血量事实 | 血回到 15 以上 |

**熔炉任务长什么样**（拆成一条条普通步骤 + 一个等待，这是关键）
```
1. 走到   熔炉 (x,y,z)
2. 熔炉放料：铁矿石×N + 燃料（煤）
3. wait_until(条件=furnace_done, 探针=熔炉(x,y,z), 等待超时=300s)   ← 不发动作
4. 走到   熔炉 (x,y,z)          ← 打架跑远了，这一步负责回来（也是 G 的验收点）
5. 熔炉取成品 → 物品探针 iron_ingot ≥ N 判成功
6. 说     「烧好 N 个铁锭，拿回来了」
```
把"回来"做成一个普通步骤而不是塞进等待里 —— 这样"被打断后要不要回去"
就是任务自己的事，跟等待无关，逻辑干净。

**新增三条"事实通道"**（手侧，跟既有的血量探针一个套路，纯本地读取、不花服务器）：
- **方块探针**：`{"cmd":"watch_blocks","list":[[x,y,z],…]}` → 快照里给 `blocks`（名字）；
- **物品探针**：`{"cmd":"watch_items","list":["cobblestone",…]}` → 快照里给 `items`（数量）；
- **熔炉探针**：`{"cmd":"furnace_watch","p":[x,y,z],"每_ms":2000}` → 快照里给
  `furnace: {输入, 燃料, 输出, 进度, 取不到?}`。实现方式（已核实 mineflayer 的能力）：
  `bot.openFurnace(block)` 拿到的对象带 `putInput/putFuel/takeOutput/fuelItem/outputItem`
  和 `progress/progressSeconds`，**进度是靠窗口的 `craft_progress_bar` 包推的**，
  所以探针要"把炉子开着"。人走远了服务端会关窗口 → 探针如实报 `取不到`（那是事实，
  不是错误），等待步骤就继续保持"未满足"、等下一步"走到熔炉"把它带回去。

  **实测补充（2026-10-01，已现场验穿）**：`进度`／`燃料进度` 只有在窗口开着的那几帧
  才有值 —— 探针是"开一下、读一眼、就关"，所以这两个字段多半是 `null`。
  **这不是 bug，是取舍**：判"烧完没有"靠的是**槽位事实**（输入在减少、输出在增加），
  比百分比进度更可靠。实测读数：输入 iron_ore 3→2→1 的同时输出 iron_ingot 1→2 ✓

**新增两个身体插件能力**（`node/plugins/body/`，零新依赖）：
- `furnace_put`（把指定物品按数量放进输入槽/燃料槽）
- `furnace_take`（把输出槽的成品收进背包）

台词/指令模板（先做这几条，够验收也够日常用）：
- 「去 X Y Z 挖 N 个 <方块>」→ [走到, 挖×N（每挖一下看一眼方块探针）, 拾]
- 「去 X Y Z，然后回来」→ [走到, 走到（起点）]
- 「任务怎么样了」→ 念当前第几步、还剩几步、重试过几次
- 「别干了」/「停」→ 中止（干净停下 + 一句回话）

## 三、一票否决：优先级与打断语义

主循环每一拍的顺序**写死**成这样（这就是"一票否决"的字面实现）：

```
0) 收尾（上一拍反击欠的后撤）
1) 节拍器（采样率）
2) 热保护 —— 超标直接挂起，连反射层都让路
3) 反射层决断 ── 不是「平静/饿等」→ 执行反射动作
                 ＋ 任务栈.暂停(原因)，这一拍**不下任务命令**
4) 任务栈 ──── 反射没事干才轮到它；它下发了命令 → 指令层这一拍不跑（不抢方向盘）
5) 指令层的持续指令（跟随之类）
```

- **暂停**：记下"第几步、暂停时刻、原因（被打/要吃饭/热保护…）"。
- **恢复**：反射回到「平静」后自动继续。**从断点那一步继续**，不重头来。
  进度信息里带"已经完成的步数"，所以恢复是幂等的（不会重复挖同一格）。
- **暂停太久**（默认 120 秒）→ 该步判失败 → 走重试逻辑（避免"被打断十次后
  还傻站在别人家门口"）。
- 每一条状态迁移都写进 `logs/任务.jsonl`：`开始/暂停/恢复/成功/失败+原因/重试/放弃/中止`。

## 四、失败与重试

- 单步 `超时`（默认 60 秒）或收到失败判据 → **记一条失败（带原因）** → 重试。
- 重试策略：**第 1 次等 1 秒、第 2 次等 3 秒**（简单退避，别把日志刷爆），
  上限 `每步重试上限`（默认 2 次）。
- 重试用完 → 整个任务判失败：**念一句人话**（"第 2 步挖 (-25,64,-25) 挖不动，
  我试了 3 次，放弃"）+ 日志留痕 + 回到平静。
- **原因必须具体**，不许写"失败了"三个字。原因来源：手侧的回执 `why`、
  超时、卡住信号、探针事实（比如"方块还是石头"）。

## 五、验收点（都拿数据验）

| # | 场景 | 期望 |
|---|---|---|
| A | 多步任务 | 3 步任务按序完成；`logs/任务.jsonl` 有每步的开始/结束；物品探针显示石头 +3；最后回到起点 |
| B | 打断与恢复 | 中途被打 → 日志出现 `暂停(原因)` → 威胁消失后 `恢复`，且**从第 N 步接着干**（不是从第 1 步） |
| C | 失败重试 | 让它挖一个挖不动的方块 → 日志里有 2 次 `重试`（带原因）→ `放弃`，并且它**说清了原因** |
| D | 一票否决 | 任务进行中被打 → **那一拍下发的是反射层的动作**（逃跑/反击），不是任务的；任务处于暂停 |
| E | 中止 | 「别干了」→ 干净停下 + 回话，日志有 `中止` |
| **G** | **非阻塞等待（烧矿 + 挨打）** | 放矿石进熔炉 → 假人触发袭击 → 战斗结束后它**回去把铁锭捡起来**；全程主循环没有一拍摄阻塞、等待超时独立生效 |
| F | 回归 | `测猎手.py`(71) / `测指令.py`(49) / 回放基准 一字不差 / 分析工具自检；新增 `tools/测任务.py` 断言全过 |

**G 的场景（写死，免得糊弄过去）**
```
1. 布场：熔炉 + 铁矿石×3 + 煤，小家伙站在旁边；把假人放在敌对名单里
2. 下令「把这 3 个铁矿石烧了，然后把铁锭带回来」
3. 任务走到 wait_until（炉子开始烧，每个 10 秒，共约 30 秒）
4. 中途让假人**动手打它**（假人加一个"打人"模式）→ 反射层立刻接管（挨打应战/逃）
5. 战斗结束、反射回到「平静」→ 任务**从第 4 步（走到熔炉）继续**
6. 期望：任务日志有 `暂停（原因：战斗，仍在等待熔炉）`→`恢复`；
   最终物品探针报铁锭 ≥3；账本里那一段等待期间**没有下发任何任务命令**（只有反射层的动作）
```
自查要点：第 3 步那段时间里，账本上应该**只有节拍/探针在动**，
一旦出现 `move/attack/jumpattack`，那必须是**反射层**发的（并伴随一条 `暂停`）。

D 的验法（这条最容易糊弄过去，所以写死）：临时把"任务第 3 步"设成"站在原地等 30 秒"，
在等待期间用假人（`tools/假人.js`）触发一次袭击，然后查账本：
**那一拍的命令必须是 `move/attack/jumpattack`，而且任务日志里紧跟着一条 `暂停`。**
只看"它最后逃掉了"不算证据 —— 要的是**同一拍**的优先级。

## 六、安全边界（主人 2026-10-01 点名）

主人原话：「**假人可别给LLM用，到时候整出来智械危机了就完蛋了**」。
这条不是玩笑，是一条架构约束，写死如下 —— 而且**做成了会失败的测试**
（`tools/安全检查.py`，13 条断言，跑一遍就知道有没有被破坏）。

1. **测试工具与主链物理隔离。** `tools/假人.js`、`tools/测*.py`、探针脚本
   这些东西**只能由命令行启动**；`node/server.js` 与 `bridge.py` **永不引用**
   `tools/` 下的任何东西。（同名注释不算，检查器只看真正的 require/import。）
2. **主链没有任何"启动进程"的能力。** 不许出现 `child_process`/`spawn`/`exec`/
   `fork` —— 也就是说，小家伙**从代码层面就没有手去开第二个客户端**。
3. **大模型层的白名单永远是"只读/移动"类**：`follow / goto / say / stop / status /
   friend`。攻击类**不在里面**，启动任何东西更不在里面；输出不过校验器一律丢弃。
4. **任务栈 fail-closed。** 任务栈只能下发**显式登记过**的动作（主链动词表 +
   身体插件能力表里的那些）；清单外的动作**一律拒绝并记账**，绝不"猜一个差不多的执行"。
   将来也不许把"启动脚本 / 开新客户端 / 执行任意命令"变成任务步骤。
5. **探针只读。** 三条事实通道（方块/物品/熔炉）只会**读**，不会写、不会动世界。

> 一句话总结这条边界：**它能不能干坏事，不取决于它想不想，取决于它有没有手。**

## 七、明确不动什么

- 反射层优先级与既有动作（跑/吃/反击/追猎/绕路）**一个字不改**。
- 隔墙判定、连击、跳劈那套战斗逻辑**不动**。
- 主链动词表**只加事实通道**（`watch_blocks` / `watch_items` / `furnace_watch`），
  **不加动作动词**。
- 大模型白名单**不加攻击类**；这一轮也不让它自由生成任务步骤。
- **不推远程仓库**（主人明确要求）。

## 八、风险与红线

- 风险：任务栈和指令层抢方向盘 → 规矩是"任务栈优先，指令层这一拍不跑"；
  新的聊天指令可以**中止/替换**任务（这是主人该有的权力）。
- 风险：等待步骤被误当成"卡住" → `wait_until` 步骤**不下发动作**，所以它
  既不会触发手侧的"卡住"检测，也不会被认为"没在干活"；超时只认它自己的
  `等待超时_ms`，跟动作超时（60 秒）**各走各的**。
- 风险：等待期间探针把快照撑大 → 探针按"整个任务用到的集合"统一挂/撤，
  任务开始挂上、任务结束撤下，中途不反复切换。
- 风险：挖矿动作会改造世界 → `canDig/canPlace` 保持关闭（寻路插件里已经是关的），
  挖只挖我们指定的那一格，绝不"顺手挖一条隧道"。
- 红线不变：CPU ≤ 60%、温度上限、内存上限照旧；任务栈每拍只是几次字典查询，
  开销可以忽略。

## 九、怎么回滚

`config.json` → `m4.task_enable = false` → `bash tools/重启.sh`。
任务栈变成哑巴（聊天里的任务模板回"我还没学这个"），反射层与既有功能一行不受影响。
代码改动集中在：`bridge.py`（新类 `任务栈` + 主循环插一层）、
`node/server.js`（两条事实通道）、`config.json`（m4.task_* 一节）、
`tools/测任务.py`（新回归）。
