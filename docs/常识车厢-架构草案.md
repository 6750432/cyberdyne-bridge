## 〇、先说三个侦察结论（都是本机实测，不是推测）

### 结论 1：**技术选型不用选 —— 数据全在本地，一个新库都不用装**

主人问「用 mineflayer 生态的哪个库、还是自己写 JSON 解析器」。实测答案：
**手侧已经把需要的东西全装好了**，只差把它们读出来。

```
~/cyberdyne-bridge/node/node_modules/
├── minecraft-data  3.117.0          ← 原版数据（含 1.21.1 全量）
└── prismarine-recipe                 ← 配方 API（备选，见下）
```

1.21.1 的数据文件就在：

```
node_modules/minecraft-data/minecraft-data/data/pc/1.21.1/
├── recipes.json     382 KB   782 条配方   ← 科技树的原料
├── blocks.json      765 KB  1060 个方块   ← 硬度 + 需要什么工具
├── items.json       165 KB  1333 个物品   ← ID ↔ 名字
└── language.json    434 KB               ← 英文名（中文用我们自己的表）
```

**实测验证过的数据形状：**

| 文件 | 结构 | 实测样例 |
|---|---|---|
| `recipes.json` | `{结果物品ID: [配方, …]}` —— **天然就是按产物建的反向索引** | `"350": [{"inShape": [[652],[652]], "result": {"id":350,"count":1}}]` |
| `blocks.json` | 每块带 `hardness` / `harvestTools` / `material` / `drops` / `diggable` | 见下 |

**`harvestTools` 就是挖掘判定矩阵，一个字都不用自己编：**

```
stone         硬度=1.5   需要 wooden/stone/iron/diamond/golden/netherite_pickaxe  → cobblestone
coal_ore      硬度=3.0   同上 6 种                                             → coal
iron_ore      硬度=3.0   需要 stone 及以上（4 种）                              → raw_iron
gold_ore      硬度=3.0   需要 iron 及以上（3 种）                               → gold_ore
diamond_ore   硬度=3.0   需要 iron 及以上（3 种）                               → diamond
obsidian      硬度=50.0  需要 diamond/netherite（2 种）                         → obsidian
oak_log       硬度=2.0   **徒手就行**                                          → oak_log
dirt / sand   硬度=0.5   **徒手就行**                                          → dirt / sand
```

**选型结论：**

| 方案 | 决定 | 理由 |
|---|---|---|
| 装新库（`minecraft-recipe-parser` 等） | ❌ 不要 | 数据已经在本地了，多一个依赖多一份风险 |
| 直接读原版 jar 包 | ❌ 不要 | 要解 jar，慢且脆 |
| `prismarine-recipe` | 🔸 备选 | 它给的是「能不能合成」的判定（手侧 craft 正用它）。**但我们要的是反向 DAG**，直接读 `recipes.json` 更直接 |
| **自己写极简 JSON 解析器，读 `recipes.json` + `blocks.json`** | ✅ **选它** | 零新依赖、零网络、可离线测、毫秒级。数据是静态的，读一次进内存缓存即可 |

★ 这也符合项目一贯的「**零依赖优先**」和「**绝不把原版数据塞进 Prompt**」。

### 结论 2：**最小闭环的配方链，本地数据里一条不缺**

```
oak_planks      ← oak_log×1                       （产出 ×4）
stick           ← bamboo×2（12 种作法）            （产出 ×1）
crafting_table  ← cherry_planks×4（11 种作法）     （产出 ×1）
wooden_pickaxe  ← cherry_planks×3、stick×2（11 种）→ ×1
stone_pickaxe   ← cobbled_deepslate×3、stick×2（3 种）→ ×1
furnace         ← cobbled_deepslate×8（3 种）      → ×1
iron_pickaxe    ← iron_ingot×3、stick×2（1 种）    → ×1
diamond_pickaxe ← diamond×3、stick×2（1 种）       → ×1
```

⚠ **但暴露了一个必须先解决的设计问题**：`wooden_pickaxe` 有 **11 种作法**
（橡木板 / 樱花木板 / 云杉木板…各一种），`stick` 有 **12 种**。

原版 JSON 里这些配方是**展开成具体变体**的，没有 tag。所以求解器会面临
「手上有橡木木板，配方表里却有 11 条，选哪条」的问题。

**设计对策：配方变体等价类。**
不引入 tag 文件，而是**从数据里自己推**：同一个「形状指纹」（`inShape` 的
行列结构 + 每格是"某类物品"）下、产物相同的那些配方，彼此的材料互为等价类。
实现上按 `(形状, 产物, 每种材料的数量)` 分桶，桶内材料即为可互换。

### 结论 3：**主链已经有一份「哪个方块要镐子」的判定 —— 但它是名字正则，会误判**

`bridge.py:1251` 的 `_要镐子()`：

```python
_镐子系 = re.compile(r"(_ore|stone|deepslate|cobblestone|bricks|concrete|obsidian|"
                     r"netherrack|furnace|anvil|terracotta|sandstone|prismarine|"
                     r"basalt|blackstone|tuff|calcite|dripstone|quartz|_block$)")
```

这是**拿方块名字猜**，没有锚定，所以：

- ✅ 大部分情况下对
- ❌ **误判**：`redstone_torch`（含 `stone`）会被判成「要镐子」
- ❌ 漏判 / 多判：拿不到"具体哪一档"（木镐 vs 铁镐），只有"要不要镐子"

**模块二的价值就在这儿**：用 `blocks.json` 的真数据**替换**这套正则猜测。

#### ★ 已经跑过对账了（1060 个方块逐个比，几分钟的活）

```
真·需要镐子的方块：385 个
【误报】正则说要镐子、其实不用：  51 个
        grass_block / bamboo_block / note_block / redstone_wire / redstone_torch /
        stone_button / snow_block / glowstone / infested_stone / …
【漏报】正则说不用、其实需要：  151 个
        granite / diorite / andesite / dispenser / spawner / iron_door /
        iron_bars / chain / brick_stairs / nether_brick_fence / …
```

**而且还有一个维度它根本表达不了**：`_要镐子()` 只回 True/False，
**不知道"哪一档"**。数据里分得清清楚楚 —— 能挖 `stone` 的镐有 6 种，
能挖 `diamond_ore` 的只有 3 种。

→ 后果：**「拿木镐去挖钻石」现在没有任何一层拦得住**，
它会走到钻石矿前面挖半天、什么东西都不掉，然后超时失败。

⚠ **但这里撞上了宪法第①条** —— 见下面「需要主人拍板的第 1 条」。

## 一、架构总览

```
┌──────────────────────────────────────────────────────────────────┐
│ L2  大语言模型（只剩三件事，严禁碰游戏常识）                        │
│                                                                  │
│   听 ：「去搞点铁」           → {"意图":"取物","目标":"iron_ingot"} │
│   说 ：「主人我没镐子喵」      ← 本地状态 → 自然语言                │
│   调度：「先造房子还是先打怪」  → 宏观优先级                        │
│                                                                  │
│   ✘ 不写步骤  ✘ 不背配方  ✘ 不管前置条件  ✘ 不塞依赖树进 Prompt    │
└────────────────────────────┬─────────────────────────────────────┘
                             │ 只传「意图」，不传步骤
┌────────────────────────────▼─────────────────────────────────────┐
│ L1  常识层（新的「生存常识」车厢 + 常识库）          ← 本方案的活 │
│                                                                  │
│   ① RecipeGraph    配方 DAG（本地 JSON 构建，内存缓存）           │
│   ② 求解器         DFS：意图 → 扁平可执行步骤链（毫秒级）          │
│   ③ 挖掘矩阵       harvestTools 真数据 → 「这把镐子挖不挖得动」     │
│   ④ 自愈           没镐子 → 自己补前置，绝不死锁                    │
│   ⑤ 监工           10 秒无进展 → 强制上报 L2 重规划                │
│   ⑥ 旅途避险       岩浆/悬崖 → 停步或绕道（分阶段，见第七节）       │
│   ⑦ 物资闭环       挖到的东西带回家进箱子                          │
└────────────────────────────┬─────────────────────────────────────┘
                             │ 已经展开成具体步骤（走现有 fail-closed 闸）
┌────────────────────────────▼─────────────────────────────────────┐
│ L0  反射层（**主链已有，一行不改**）                              │
│   跑 / 吃 / 保命 / 还手 —— 一票否决，<50ms，永远压在 L1 上面       │
└──────────────────────────────────────────────────────────────────┘
```

**关键分工变化（相对现状）：**

| | 现在 | 改后 |
|---|---|---|
| 谁写步骤 | L2（大模型写任务书） | **L1（本地求解器展开）** |
| 谁背配方 | 没人背（所以它一直不会合成前置） | **L1 的 RecipeGraph** |
| L2 的输出 | `{"任务":{"步骤":[…]}}` | `{"意图":"取物","目标":"iron_ingot"}` |
| Prompt 里有什么 | 步骤类型清单（9 个词） | **意图词表（十几个词）+ 不带任何配方** |

★ **L2 的输出变小了**，这是好事：prompt 从 1600 字有望降到 800 字以内，
而且**幻觉面积大幅缩小**（它再也写不出一个格式错的任务书，因为不写了）。

## 二、模块一：RecipeGraph + DFS 求解器

### 2.1 数据加载（一次，缓存）

```
读 recipes.json  →  {产物名: [ {形状, 材料:{名:数}, 产出数, 需要工作台?}, … ]}
读 blocks.json   →  {方块名: {硬度, harvestTools, material, drops, diggable}}
读 items.json    →  {名↔ID}（recipes.json 里全是数字 ID，必须转名字）
```

**构建耗时预估**：三个文件加起来 1.3 MB JSON，Python `json.load` 大约
**50~150 ms**（本机是机械盘，冷读可能到 300 ms）。所以：
**只在车厢装载时读一次，之后常驻内存**，绝不每步重读。

### 2.2 节点分类（主人的第 3 条要求）

求出依赖后，每个叶子节点必须归到三类之一：

| 类别 | 判定依据（全来自本地数据） | 处理 |
|---|---|---|
| **合成获取** | `recipes.json` 里有这个产物 | 继续往下递归 |
| **挖掘获取** | 某个方块 `drops` 里含它 | 关联该方块的 `harvestTools` → 需要哪一档镐子 |
| **击杀/掉落获取** | 既没配方、也不在任何方块 drops 里，但在 `items.json` 里 | 标为「需外部获取」，上报 L2 |
| **不可达** | 上面三条都不满足 | **立刻报「当前条件无法达成」，绝不死循环** |

★ 主人点名要的「没钻石镐挖黑曜石 → 立刻报错」就是**第 4 类 + 最大深度限制**
联合拦下来的：深度超限 → 报错，不是无限展开。

### 2.3 DFS 求解器

```
求解(目标, 数量, 背包快照, 深度=0):
    若 背包够 → 返回 []（这一步不用干）
    若 深度 > 上限(默认 8) → 抛「超纲」
    若是 合成获取 → 选一条最优配方 → 对每个材料递归 → 拼成 [ …前置 , 合成我 ]
    若是 挖掘获取 → 找出该方块的 harvestTools
                   若 背包里的工具 ∩ harvestTools ≠ ∅ → 返回 [走到, 挖]
                   若 空 → **先递归求工具** → 再返回 [ …工具链, 走到, 挖 ]
    否则 → 抛「无法达成：<原因>」
```

**几个必须处理的细节：**

1. **换工具要先装备**。挖的东西换了档（挖完石头要挖铁），得先合成/换上石镐。
2. **工作台**。手侧的 `craft` 逻辑是：先试 2×2 手工合成，不行就找**4 格内**的
   工作台。所以求解器在展开「需要工作台」的配方时，必须插三步：
   `合成工作台 → 走到空地 → 放工作台 → 走到工作台旁`。
   ★ 「放工作台」用的是现有的 `放`（place）动作，不需要新命令。
3. **材料数量取整**。MC 的配方产出常是 4 或 3，要按 `ceil(需要/产出)` 反推原料，
   而且**要按已用掉的部分扣减**（同一批木头不能算两次）。
4. **产物复用**。链子里多处需要木板，不能各算一次。

### 2.4 输出形态

求解器输出**扁平的步骤表**，直接交给现有的 `任务栈.接()`：

```json
[{"动作":"走到","p":[…],"到点":2.5},
 {"动作":"挖","p":[…],"为什么":"橡木原木（徒手就能挖）"},
 {"动作":"合成","物品":"oak_planks","数量":4},
 …]
```

★ **这是本方案最漂亮的一点**：求解器只是「**批量填任务书**」的另一种写法，
展开出来的步骤**照样逐条过现有的 fail-closed 闸**（危险物品 / 参数完整性 /
白名单 / 攻击类红线），一道都不少。跟「受限脚本」车厢是同一个哲学。

⚠ **但要注意一个实测约束**：`翻译器._校验任务()` 里有 `max_steps=6` 的限制。
L1 走的是 `任务栈.接()`，**不经过那个限制**（那是给大模型任务书设的）。
不过 `接()` 拿到几十步会怎样（`_挂探针` 会建很大的 watch 列表），
**需要在阶段一实测**，必要时分批交付。

## 三、模块二：挖掘判定矩阵

主人要三件事，逐条对应：

### ① 硬性：必须用特定等级以上镐子的方块

**直接用 `blocks.json` 的 `harvestTools`**，一个字节都不用自己编。
实测已经验证过 10 种关键方块的档位（见第〇节结论 1）。

需要注意：`harvestTools` 是**集合**，不是"最低档"。所以：
- 判定 = 「背包里有没有**任何一把**在集合里的镐子」
- 要展示"最低档"给人看，得先算出**档位序**：
  按「这个工具能挖的方块集合」做**集合包含**排序。
  ★ **实现时必须先验证这些集合是否全序**；如果不是全序（有交叉），
  就退化为**逐方块独立判定**，不硬排档位。

### ② 软性：徒手能挖的绝不死锁

`harvestTools` 为空 = 徒手就能挖（木头、泥土、沙子、草方块…）。
**必须放行**，只是慢。主链现在的 60 秒步骤超时够用（实测挖一个原木 ~1 秒）。

### ③ 效率：有工具优先用

`blocks.json` 有 `hardness`，但**没有「某工具对某方块的挖掘倍率」**。
原版的倍率表是：木 2× / 石 4× / 铁 6× / 钻石 8× / 金 12×，可徒手 1×。

**对策**：倍率表写死在这节车厢里（**5 个数**，不是配方表，不违反"严禁硬编码配方"），
或者**先不做效率优化**（阶段一不必要）—— 让 B 选项。

## 五、模块：旅途避险与超时自愈（主人标「最重要」）

### 5.1 现有能力盘点（**不要重复造**）

主链 L0 反射层已经有：**跑 / 吃 / 保命 / 还手**，而且是**一票否决**，
永远压在任务栈上面。任务栈碰到反射层有事会自动**暂停**、事后**从断点恢复**。

所以「半路暴死」这件事，**现在已经有第一道防线了**。新增的应该是**第二道**：
**主动趋避**（在还没进入反射层的触发范围之前就绕开）。

### 5.2 分阶段（★ 必须分，不然会做不完）

| 阶段 | 做什么 | 难度 |
|---|---|---|
| **一** | **不做避险**。只在链子生成时做**静态检查**：目标在 64 格内、路径上有岩浆就拒绝 → 上报 | 低 |
| **二** | 动态威胁评估：按 血量/装备/敌人数量种类 决定 打 / 绕 / 躲 | 中 |
| **三** | 岩浆与悬崖：**强制停步 + 上报**（先做这个） | 中 |
| **四** | **搭桥**（岩浆上搭路、悬崖搭柱） | **高 —— 见下** |

⚠ **关于「搭桥」的诚实说明**：
手侧现在**没有**「边走边在脚下放方块」这个原语。`放` 是「在指定坐标放一个方块」，
配合寻路走一步、再放一块，理论上能做，但**节奏极难控**（MC 里搭桥要
边退边放，时序错了就掉岩浆）。我建议**阶段一二三都只做「停步 + 绕道 + 上报」**，
搭桥留到有真实需求再说。**硬做搭桥的预期收益率很低，风险很高。**

### 5.3 10 秒无进展 → 强制上报（主人红线）

**这条要先把「进展」定义清楚**，否则会误伤：

我提议的「进展」定义（三条满足任一即可）：
1. 任务的**步骤号**前进了
2. 坐标变化 > 1 格（真的在动）
3. 背包里**目标物品的数量**增加了

**三条都连续 10 秒没发生** → 判为「卡住」→ 停任务 → 上报 L2 重规划。

⚠ **但这里和主链现状有冲突**：主链的步骤超时是 **60 秒**（走/挖/放 各走各的），
重试 3 次。主人的 10 秒比它短得多。

**两个方案：**
- **甲**：10 秒只做**上报**（L2 知道它卡了），主链的 60 秒超时**照旧**，互不干扰
- **乙**：10 秒就**打断**主链的任务（L1 直接调 `任务栈.暂停()` + 上报）

**我倾向甲**：乙会和主链的重试机制打架（主链正重试，L1 把它打断，两边都不知道
对方在干嘛）。而且「挖一个深层矿石」在 10 秒内没进展是**正常**的。
**这条需要主人拍板，见第九节第 3 条。**

### 5.4 卡死自愈

主人举的例子：「卡在蜘蛛网」。

`harvestTools` 里没有蜘蛛网（它徒手可挖）。所以自愈动作可以是：
**卡住 → 挖掉脚下的/挡路的那个方块 → 重新算路**。
现有 `挖` 动作就够。

## 六、车厢切分方案

主人说「一个全新的常识车厢」。我建议**切成一块「库」+ 一节「车厢」**：

```
外挂/常识/                       ← 纯 Python 包，**不是车厢**，不改 bridge 任何东西
├── 数据.py                     读三个 JSON，建缓存
├── 配方图.py                   RecipeGraph：DAG + 变体等价类
├── 求解器.py                   DFS：意图 → 扁平步骤链
├── 挖掘矩阵.py                 harvestTools → 「这把镐子挖不挖得动」
└── 测常识.py                   纯函数测试（毫秒级，不用起车）

外挂/生存常识/                   ← **车厢**（顺序 50，排在现有四节后面）
├── manifest.json
└── 补丁.py                     ① 包 翻译器（意图 → 求解）
                                ② 替换 _要镐子（用真数据）
                                ③ 监工（10 秒无进展）
                                ④ 同步实例()
```

**为什么这样切：**

- 「库」是纯函数，**可以离线测到死**（几百条断言，毫秒级），
  不需要起车、不需要开 MC。这是本项目的传统打法。
- 「车厢」只做**接线**，薄薄一层，出问题好定位。
- 将来「旅途避险」可以再开一节车厢（顺序 60），互不干扰。

**为什么顺序 50（排最后、最外层）：**

车厢是**后挂的先执行**。L2 的输出要先经过「生存常识」转成步骤，
再往下走「任务书体检」「受限脚本」「动作面」的闸。
排最外层正好是这个次序。

## 七、同步实例() 设计（主人点名的红线）

主人要求「热插拔不丢任务进度」。需要缓存的东西：

| 缓存 | 在哪 | 热插拔怎么办 |
|---|---|---|
| RecipeGraph | 车厢模块的内存 | 摘了就没，重挂时**重新构建**（~150ms，可接受）。**不需要同步** |
| 当前任务链进度 | **主链的任务栈实例**上 | ★ **必须同步** —— 见下 |
| 当前手持工具 | 主链状态帧里，每 1Hz 刷新 | **不需要缓存**，每次现读 |
| 已消耗的材料账 | 求解器的账 | ⚠ **需要**：热插拔后重算会算错 |

**`同步实例()` 要做的两件事：**

1. **读回进度**：从 `车钩.活实例("任务栈")` 拿到活着的任务栈实例，
   读 `实例.任务`（当前链子、第几步），存进车厢自己的缓存
2. **热挂时接上**：如果挂上来的时候 `任务栈` 正跑着一条**本车厢生成的**链子，
   不要重头算，接着往下跑

★ 具体机制：车厢生成的每个任务，在 `任务` 里塞一个**私有标记**
（比如 `任["_常识链"] = True` 和 `任["_常识账"] = {...}`）。
`同步实例()` 认这个标记：

- 有标记 → 这是我生成的活儿，把账接回来
- 没标记 → 别人的活儿，我不管

**这正是「活实例探针」的第二个用途** —— 第一个用途（热挂动作面时同步
`翻译器.合法步骤`）已经在 2026-10-07 做完并实机验证过了。
**这套基础设施现成，不用新造。**

## 八、缺的能力（诚实清单）

有些主人要的功能，**现在的手侧做不到**，必须说清楚：

## 九、★ 需要主人拍板的 6 个点

### 1. 宪法第①条要不要放宽？

现在 `车钩` 的宪法①是：**`vars(bridge)` 里所有顶层对象的身份都不许变**。
这条是为了防「车厢偷偷换掉 `bridge.主`」。但它同时也**挡住了**用真数据替换
`_要镐子()` 这种模块级辅助函数。

**三个选项：**
- **甲**：不放宽。模块二就不替换 `_要镐子`，改成**在它之前拦**（本车厢自己判定，
  主链那个正则永远走不到）。**代价**：主链的判断仍在，是"两套并存"
- **乙**：宪法①升级为**两档** ——
  「绝对不许换」：`主`/`任务栈`/`翻译器`/`反射层`/`指令层`/`心跳`/`记忆` 这些顶层类
  「**铭牌申报后可以换**」：其它顶层**函数**（车钩记档 + 体检报告里列出来）
- **丙**：完全放开

**我推荐乙**：它是有原则的细化，不是放水 —— 而且实机每天都会碰到"想修一个小函数"
的场景，甲方案会让常识车厢一直带着一个补不掉的已知错误。

### 2. 10 秒上报：只上报，还是也打断？（见 5.3）

我推荐**只上报**（方案甲）。

### 3. L2 的角色切换怎么落地？

现在的 `心跳` 让大模型**自己定目标、自己写步骤**。新架构里它只该做**调度**。
**要不要保留「自主定目标」这个能力？** 我的建议：**保留，但目标从"写步骤"变成
"提意图"** —— 它还是可以自己决定"我想去挖点铁"，只是不再自己解前置。

### 4. 「家」的坐标怎么定？

任务书里的「带回家 → 放进指定箱子」需要一个家的位置。
建议：**在 config.json 里加一个 `常识.家的箱子` 坐标**，或由主人在游戏里指一次。

### 5. 阶段一的最小闭环，验收标准写成什么？

我的提案（**请主人确认或修改**）：

> 在一个**全新的、没有任何工具**的环境下，给小家伙一句
> 「我要一把石镐」。全程**不调用大模型**（把 `m3.llm.enable` 关掉验证），
> 它自己完成：**徒手撸树 → 木板 → 工作台 → 木镐 → 挖石头 → 石镐**，
> 并把这把石镐**拿在手上**说出「石镐做好了」。
> 判据：**石镐真的出现在背包里**（读背包，不看它说的话）。

★ 注意这里有个**跟主人原话的差别**：主人写的是「徒手撸树 → 做木镐 → 挖石头 →
做石镐」，我加了一句「**拿在手上**」。因为"合出来"和"能挖东西"之间还隔着
"装备"这一步（见第八节）。**这条要实测才知道能不能做到。**

### 6. 主链那份「名字正则」的误判 —— **证据已经跑出来了**

拿 1060 个方块逐个对账 `bridge.py:1251` 的 `_要镐子()`：

```
真·需要镐子的方块：385 个
误报 51 个（grass_block / redstone_torch / stone_button / glowstone / …）
漏报 151 个（granite / diorite / andesite / dispenser / spawner /
            iron_door / iron_bars / chain / brick_stairs / …）
```

**这不是"要不要修"的问题，是"这个数能不能忍"的问题。** 请主人看一眼再定第 1 条。
